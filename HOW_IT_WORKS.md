# Как работает лаба №1 — объяснение для новичка

## Общая картина

Блочный шифр (например, DES) умеет шифровать **только блок фиксированной длины** — например, 8 байт. А файлы имеют произвольную длину. Отсюда два вопроса, которые решает контекст (`cryptoctx`):

1. Что делать, если данные не делятся ровно на блоки? → **набивка** (`pad`/`unpad`)
2. Как из «шифрования одного блока» получить «шифрование всего файла», чтобы одинаковые куски текста не превращались в одинаковый шифротекст? → **режимы шифрования** (ECB, CBC, ...)

Поток данных всегда такой: `данные → набить до кратности блоку → порезать на блоки → прогнать через режим → шифротекст`.

## Набивка — `lab1/internal/models/modes.go`

`n := bs - len(data)%bs` — сколько байтов не хватает до полного блока. Пример: блок 8, данных 21 → 21 % 8 = 5, нужно добить 3 байта.

Четыре способа добить:

- **Zeros** — просто нули. Минус: при дешифровке непонятно, сколько нулей срезать (файл мог сам кончаться нулями).
- **ANSI X.923** — нули + **последний байт = сколько добавили** (тут 3).
- **PKCS#7** — каждый добавленный байт равен числу добавленных: `03 03 03`.
- **ISO 10126** — случайные байты + последний = число.

Всегда добавляем хотя бы 1 байт: если данных ровно 8 — добавляем целый блок набивки. Иначе последний байт исходных данных можно было бы ошибочно принять за длину набивки.

`unpad` проверяет длину и содержимое набивки, затем срезает хвост. Для Zeros удаляет все завершающие нули, включая исходные: для произвольных файлов используется PKCS7. ISO10126 заполняется псевдослучайными байтами через `math/rand`; готовые криптоалгоритмы и пакеты `crypto/*` не используются.

## Режимы шифрования — `applyMode`

- **ECB** (Electronic Codebook) — тупо шифруем каждый блок независимо. Быстро, но одинаковые блоки дают одинаковый шифротекст (классическая картинка «зашифрованный пингвин виден сквозь шифр»). Поэтому в одиночку его никто не использует, но по ТЗ он есть.
- **CBC** (Cipher Block Chaining) — перед шифрованием XOR-им блок с **предыдущим шифроблоком**. Первый блок — с **IV** (initialization vector, случайное число, не секрет). Теперь одинаковые блоки дают разный шифротекст. Расшифровка: дешифруем блок, XOR с предыдущим шифроблоком.
- **PCBC** — как CBC, но XOR идёт с парой «предыдущий исходный ⊕ предыдущий шифро». Мелочь в реализации, отличается одной строчкой feedback.
- **CFB** — шифр превращаем в поток: шифруем IV → получаем гамму → XOR с данными → шифроблок становится следующим IV.
- **OFB** — как CFB, но в цепочку подаём зашифрованный IV, а не шифротекст.
- **CTR** — шифруем счётчик (IV, IV+1, IV+2...), XOR с данными. Можно шифровать блоки **параллельно**, т.к. счётчики известны заранее.
- **RandomDelta** — здесь реализован вариант CTR с заданной положительной **нечётной** дельтой: `IV`, `IV+delta`, `IV+2*delta`, ... По умолчанию дельта равна 1; в демо — 257. Счётчик big-endian, сложение — по модулю `2^(8*BlockSize)`. Нечётная дельта обеспечивает полный период счётчика; CTR и RandomDelta отклоняют сообщение, которому требуется больше блоков, чем этот период, включая набивку. Чётные дельты теперь отклоняются: например, для DES шаг `2^62` повторяет гамму уже через четыре блока.

ТЗ только называет Random Delta, не задавая формулу. Приведённое определение — выбранная в проекте трактовка; её соответствие материалам преподавателя нужно сверить отдельно.

Важно: CFB/OFB/CTR/RandomDelta вообще не используют `Decrypt` блочного шифра — шифрование и расшифровка делаются одной и той же XOR-операцией с той же гаммой.

## Ключевые места кода

`lab1/internal/models/cryptoctx.go` — асинхронность: `go func() {...}` запускает работу в фоне, а результат прилетает в канал `<-chan Result`. Вызов `res := <-c.EncryptBytes(...)` ждёт этот канал. Сначала проверяем `res.Err`, затем используем `res.Data`; вход и `dst` нельзя менять до получения результата. Недостаточный `len(dst)` возвращает ошибку, а не усечённый результат.

`parallelBlocks` делит данные на диапазоны, ограничивая число воркеров `GOMAXPROCS`. Параллельны ECB, CTR/RandomDelta и расшифрование CBC/CFB. Шифрование CBC/CFB, PCBC и OFB последовательны: следующий шаг зависит от предыдущего.

`NewContext` принимает **фабрику**, а не готовый шифр: каждый контекст создаёт и настраивает собственный экземпляр. Фабрика обязана возвращать новый независимый объект, а не одну общую ссылку. Пример создания DES-контекста:

```go
ctx := cryptoctx.NewContext(
    func() interfaces.BlockCipher { return des.NewCipher() },
    cryptoctx.CBC, cryptoctx.PKCS7,
    []byte("8bytekey"), []byte{1, 2, 3, 4, 5, 6, 7, 8},
)
```

Это изменение API: старый первый аргумент `cipher` заменяется фабрикой. Nil-фабрика, nil-шифр и недопустимый ключ вызывают `panic` при создании; ошибки режима, набивки и I/O возвращаются через канал операции.

Контекст копирует IV в конструкторе, а каждая операция получает отдельное состояние режима. Изменение исходного IV и параллельные операции не портят состояние друг друга. Настроенный шифр должен допускать параллельные `Encrypt`/`Decrypt` и возвращать независимые результаты. Вызывать `SetKey` одновременно с обработкой блоков нельзя. Контекст не генерирует свежий IV между сообщениями; контроль периода не защищает от повторения IV в разных операциях.

### Файлы — `lab1/internal/models/file.go`

Файлы обрабатываются порциями по 64 КиБ (с выравниванием на размер блока), а состояние режима переносится между порциями. Набивка добавляется только в конце файла и снимается с последнего блока. Для Zeros запоминается позиция последнего ненулевого байта, затем результат обрезается: даже длинный нулевой хвост не требуется хранить в памяти.

Результат сначала записывается во временный файл в каталоге назначения с правами `0600`. После успешной обработки, проверки набивки, `Sync` и `Close` он заменяет назначение через `Rename`; одинаковые входной и выходной пути допустимы. Биты доступа существующего обычного файла сохраняются. Ошибка до замены не обрезает старое назначение; ошибки очистки временного файла также возвращаются. На Unix замена атомарна, вне Unix `os.Rename` такой гарантии не даёт. Символьная ссылка назначения заменяется как запись каталога, а не используется для записи в её цель. Это не гарантия сохранности при отключении питания: каталог после переименования отдельно не синхронизируется.

## Сеть Фейстеля — `lab1/internal/feistel/feistel.go`

DES устроен как сеть Фейстеля: блок делится пополам на L и R, и 16 раз делаем `L, R = R, L ⊕ F(R, ключ_раунда)`. Раундовая функция F может быть даже необратимой: обратный раунд — `L, R = R ⊕ F(L, ключ_раунда), L`, ключи используются в обратном порядке.

Сеть копирует исходный ключ перед расширением и сохраняет глубокую копию расписания. Раундовая функция получает копии половины блока и раундового ключа, поэтому может менять их на месте, не разрушая обратимость сети и сохранённые ключи. Для параллельной работы `Transform` должен быть потокобезопасным; его результат нельзя перезаписывать другими вызовами. Таблицы DES доступны только внутри пакета.

## DEAL — `lab1/internal/deal/deal.go`

Блок — 16 байт, раундовая функция — собственный DES. Для ключей 16/24 байта используется 6 раундов, для 32 байт — 8. В DEAL формула зеркальная: `L, R = R ⊕ DES_key(L), L`, поэтому адаптер меняет половины местами до и после общей сети.

Раундовые ключи получаются цепочкой DES-CBC с нулевым IV и фиксированным ключом `0123456789ABCDEF`. После первого прохода частей исходного ключа добавляются маски `80...`, `40...`, `10...`, `01...` по описанию Кнудсена. Настроенные DES-шифры кешируются по раундовым ключам; кеш безопасен для параллельных вызовов.

## Запуск и ограничения

Из `lab1/`: `go run ./cmd` (либо `go run -race ./cmd` для обнаружения гонок). Общее демо проверяет DES и DEAL-128 на байтах во всех 28 сочетаниях режима/набивки, затем на пяти файлах из `data/` с PKCS7: текст, исходник, BMP, WAV и AVI. `video.avi` — синтетический несжатый клип 32×24, четыре кадра за одну секунду, созданный генератором `ffmpeg testsrc`; для запуска демо ffmpeg не нужен.

Результаты — `data/enc/{DES,DEAL}/`. Файлы обрабатываются ограниченным пулом воркеров, шифрование и сравнение выполняются потоково без загрузки целых файлов в память. В штатном запуске выводится 126 строк `OK`: 56 для байтов и 70 для файлов. `demo.Run()` возвращает объединённую ошибку, а CLI при сбое пишет её в stderr и завершается с кодом 1.

Постоянных файлов `*_test.go` нет. `go test ./...` проверяет сборку пакетов, но сообщает `[no test files]` и не является подтверждением корректности алгоритмов; новые тесты по текущему запросу не добавлялись.

Это учебная реализация, **не защита реальных данных**: DES устарел, а аутентификации нет. Фиксированные ключи и IV допустимы только в воспроизводимом демо; повторять IV под одним ключом в реальном применении нельзя. Корректная набивка не гарантирует целостность. Исправления DEAL и переноса CTR/RandomDelta изменяют шифротекст относительно старого кода; старые результаты демо следует пересоздать.

## Контрольный вопрос для самопроверки

Почему в CTR-режиме при расшифровке `Decrypt` блочного шифра не вызывается вообще?

*(Ответ: потому что CTR — потоковый. Гамма = E(IV), E(IV+1), ... при расшифровке она точно такая же, как при шифровании (тот же ключ, тот же IV). Исходный текст = шифротекст ⊕ гамма. Шифрование гаммы — единственная операция с шифром, и она одинакова в обе стороны.)*
